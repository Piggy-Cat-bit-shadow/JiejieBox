# Upstream retirement, batch 2: the lean maintained-patch index (audit Q47)

Batch 1 answered "which fork commits have an identical upstream patch" mechanically. Batch 2's object is the other side: the commits upstream does **not** carry, "grouped into logical patches, each with trigger/regression/consumer". That population is history, not a patch list - months of merges, rebases and rewrites, most commits with no maintenance marker - so a per-commit trigger cannot be derived without adjudicating each one, and writing thousands of generated rows would look like completion while saying nothing.

This batch therefore builds the **lean** index the audit's wording asks for: the logical patches the fork still marks as its own. A patch is in scope when a source or documentation line carries a `SPEC <id>` reference. The marker text is the trigger evidence, the files are the consumers, the tests that carry the same `SPEC <id>` are the precise regression reference, and the patch-id makes the retirement decision mechanical.

This page and `upstream-retirement-batch2.tsv` are generated by `scripts/ci/upstream-retirement-batch2.py --write`; `--check` fails when either file no longer matches the tree.

## What each column means - and does not

- **commit_shas / patch_ids** are the blamed commits for the marker lines and their `git patch-id --stable` values. Retirement is decided by patch-id equality with an upstream candidate, so the value has to be in the row; without it every retirement review re-derives it by hand.
- **trigger_marker** is the marker comment with `file:line`. It is the source of the trigger claim for review, NOT a rewritten "user-visible symptom" paragraph. The ledger's own files are excluded: a sentence about the index is not evidence about the patch, and the first version of this tool ingested exactly that.
- **consumer_files** is every file carrying that SPEC id - the patch's footprint, not a proven list of runtime call sites.
- **regression_exact** lists the test files in those packages that carry the same `SPEC <id>`. That is a precise reference, and still not a claim that the test exercises this patch. **regression_surface** is the count of test files available in those packages; a large number there is not evidence of coverage.
- **upstream_status / upstream_commit** are measured, never assumed: `absorbed` when the commit itself is in a local upstream ref's history; `duplicate-of-upstream` when batch 1's recorded comparison found an upstream commit with the same stable patch-id (that commit id is `upstream_commit`); `fork-only` when the recorded comparison covered this commit and found no equal patch-id; `not-comparable` only when no measurement covers it. The first version of this tool wrote "upstream has no equivalent patch-id" for every code row without ever asking - a state the tree could not support.
- **disposition** is HOLD for code rows upstream does not carry, ANALYSIS for historical investigation records with no code patch to retire, and RETIRE_READY only when upstream already ships the change (`absorbed` or `duplicate-of-upstream`).
- **retirement_condition** is what has to become true, and **retirement_verify** is the command that decides it.
