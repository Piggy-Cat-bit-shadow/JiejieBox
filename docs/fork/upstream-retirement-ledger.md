# Upstream retirement ledger — which fork patches upstream already carries

Read-only analysis. This is the **minimum index** the closeout audit asked for (Q47): for the patches
this fork still carries, what has to be true before one can be dropped, and how to check that.

It does not replace `FORK_REPOSITORIES.md`, `docs/fork/fork-patchids.tsv` or
`docs/fork/upstream-53-ledger.md`; it says what those two **cannot** answer, and adds the mechanical
part they were missing.

## What was measured (2026-11-12, `upstream/testing` = `a13dbe1f7`, no fetch)

| Fact | Value | Command |
| --- | --- | --- |
| Non-merge commits in `HEAD` | **6727** | `git log --no-merges --format=%H HEAD \| wc -l` |
| Non-merge commits reachable from the pinned upstream tip | **2950** | `git log --no-merges --format=%H upstream/testing \| wc -l` |
| Upstream commits `HEAD` does **not** contain | **0** | `git rev-list upstream/testing --not HEAD \| wc -l` |
| `fork-patchids.tsv` fork commits reachable from `HEAD` | **0 of 4354** | membership test against `git rev-list HEAD` |

### Two premises that had to be corrected

1. **`docs/fork/fork-patchids.tsv` describes a different history.** Its 4354 fork SHAs are **not**
   reachable from `HEAD` (the fork history was rewritten); 2773 of its upstream columns are reachable
   from the pinned upstream tip and 1581 are not. It answers "which upstream commit did this *old*
   fork commit correspond to", not "which patch I still carry can be retired".
2. **The "53" in `docs/fork/upstream-53-ledger.md` is an empty set at this pin.** That ledger was built
   against fork `912ed1ef` and upstream `6afeff4c`. `git rev-list upstream/testing --not HEAD` is now
   **0**: `HEAD` contains every commit of the pinned upstream. The ledger remains a valid historical
   analysis of that rebase; it is not a current gap.

## The classification (patch-id is the judge)

`git patch-id --stable` exists to answer "is this the same change". Applied to both trees' non-merge
commits:

```
emit() { : > "$2"; git log --no-merges --format='%H' "$1" | while read -r c; do
  git show --no-color --format= "$c" | git patch-id --stable | awk '{print $1"\t'"$c"'"}'; done >> "$2"; }
emit upstream/testing /tmp/up_pids.tsv
emit HEAD             /tmp/head_pids.tsv
```

| class | count | disposition | retirement trigger | verification |
| --- | --- | --- | --- | --- |
| same patch-id, **same SHA** | 2947 | nothing to do (the branch already contains the upstream commit) | — | `git merge-base --is-ancestor <sha> HEAD` |
| same patch-id, **different SHA** | **218** | **retire-ready** (duplicate copy of an upstream change) | already met; absorbed at the next rebase onto upstream | both sides `git show <sha> \| git patch-id --stable` print the same id |
| no upstream patch-id | 3562 | HOLD — still fork-only | upstream gains an equivalent patch-id, or the fork decides to follow upstream's implementation | the same check, **different** today |
| upstream-only | 0 | — | — | `git rev-list upstream/testing --not HEAD` |

2947 + 218 + 3562 = 6727, the whole non-merge history.

Spot check, reproducible:

```
$ git show 9f1cd1ef7 | git patch-id --stable
357444932f9c717800da1bdc3b0954a50bcc81b3 0000000000000000000000000000000000000000
$ git show dd897389b | git patch-id --stable
357444932f9c717800da1bdc3b0954a50bcc81b3 0000000000000000000000000000000000000000
```

Both commits also carry the same author/committer time (`2026-11-03T03:07:31Z`): one logical change,
two SHAs, in two histories.

The 218 rows (fork SHA, upstream SHA, subject, both dates) are recorded with the closeout evidence
(`q47_batch1_duplicate_patches.tsv`); they are not committed here because the row set is a snapshot of
two trees and is regenerated by the commands above.

## What this does NOT claim

- **The 218 are not deleted, and cannot be deleted from here.** They are history-rewrite decisions
  (rebase vs merge vs cherry-pick set), not content decisions. The provable part is that upstream owns
  an identical patch.
- **The 3562 fork-only commits are not judged necessary.** "Upstream has no equivalent patch" says
  nothing about whether the change is still wanted; that is the per-topic adjudication still owed.
- **The pin did not move.** `upstream/testing` is a local remote-tracking ref; no fetch was run, so
  "upstream-only = 0" is a statement about *that ref*, not about the live tip.
- Merge commits are excluded on both sides, and empty patch-ids (empty or pure-binary commits) are
  skipped.
