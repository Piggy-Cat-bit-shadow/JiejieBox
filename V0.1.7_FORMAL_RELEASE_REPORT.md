## 2. A release-blocking defect was found, and it was MINE

The first build wave failed three of five workflows, all at their BUILD-INFO step, with the same
error on three different platforms:

```text
./scripts/ci/build-info.sh: line 118: mobile_tags: unbound variable
```

**Cause.** My earlier Android BUILD-INFO change added a `mobile_tags` field, and the line that emits
it tests the name unconditionally — but only the ANDROID branch ever sets it, while `build-info.sh`
runs under `set -u`, where an unset name is fatal. So linux, darwin and windows records all aborted.
`build_profile` had already been given an explicit empty default for exactly this reason;
`mobile_tags` had not. Fixed in `6cfdc9ace`, which adds both defaults and is otherwise inert (13
insertions, no deletions).

Because the fix changes the tree, `FINAL_RELEASE_SHA` moved with it and the tag was moved after it.
The alternative — reverting the Android change instead of fixing it — was rejected: the change is a
legitimate improvement and the defect is a one-line omission, so fixing forward is correct. The §4.2
precondition was re-checked before the second move: still no Release.

**This is exactly what §23 anticipates, and nothing was hidden**: the failure, the cause, the fix and
the tag move are all recorded here.

### 3.1 The macOS blocker, and why it is not a product defect

Two consecutive macOS runs failed, in the same step but on **different tests**:

```text
#232  388e51f75 / 6cfdc9ace   unit tests (macOS tags)   TestAdvGItem7OccupiedPortIsInvisible-
                                                        WhileTheReopenIsInFlight
                                                        (transport/wireguard)
#233  6cfdc9ace              unit tests (macOS tags)   TestNeitherLaneStarvesWhenBothAreBusy
                                                        (common/trafficsched)
                                                        "0" is not positive — NORMAL must never
                                                        be starved by a busy high-priority lane
```

Both are timing-sensitive liveness tests, in packages my commit does not touch —
`6cfdc9ace` changes one file, `scripts/ci/build-info.sh`, and nothing else. And the same step passed
at `388e51f75` (run #230).

So this is **flaky-test evidence, not a product defect**: the failing test changes between runs on
the same code, in packages unrelated to the change. That distinction matters and is stated plainly —
but it does **not** make the state releasable. §12 requires every release-blocking workflow to be
green, and §13 forbids skipping a gate because a release is imminent.

**Next action, stated concretely:** either re-run macOS until it passes and record that the gate was
satisfied by a re-run of a known-flaky test, or make `common/trafficsched`'s liveness tests
deterministic before the release. Choosing between those is a maintainer decision about product
quality, not plumbing — which is why the release stops here rather than proceeding on a re-run.
