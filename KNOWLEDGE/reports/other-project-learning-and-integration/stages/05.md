## P01 首批（已落地）

### 事实与边界

- `common/urltest.Coordinator` 已是 **per-Box** 的测量并发上限（`C.URLTestConcurrency`，box.go 注册到 ctx）；
  所有真实网络测量都经过 `Measure`，因此自动组检查、Clash delay、原生单节点/组测试、endpoint 测试都在
  同一预算下。`Measure` 在拿到槽位后才启动探测 deadline，排队时间不冒充节点超时。
- 本轮补的是**队列次序**：此前槽位是 FIFO 信号量，后台饱和时交互探测只能排在整轮后台之后。

### 实现

- `Coordinator` 从 `chan struct{}` 改为受锁保护的 `inFlight + queue`：
  - `Acquire(ctx)` 后台、`AcquirePriority(ctx)` 交互；同一上限，只有排队次序不同；
  - 释放时优先授予最早的交互 waiter；`priorityAgingEvery = 3` 次连续交互授予后，强制服务最早的
    后台 waiter，后台不会永久饥饿；
  - waiter 是 `{priority, ready, granted}` 小结构，取消时在锁内移除；授予与取消同时发生时归还槽位；
  - 释放闭包 `sync.Once`，重复释放不会多还槽位。
- `Measure` 按 `adapter.IsBackgroundProbe(ctx)` 选择 `AcquirePriority`/`Acquire`：探测起源仍由 04 的
  `runtimecoord` 标记决定，没有新增第二个优先级来源。
- 没有新增 worker/队列框架：同一 Coordinator 继续服务所有既有触发入口。

### 测试

`common/urltest/coordinator_priority_test.go`：
- 交互 waiter 越过两个已排队的后台 waiter，先拿槽位；
- 连续 3 次交互授予后，后台 waiter 被老化服务，随后交互继续——顺序确定，不依赖计时器；
- 取消的交互 waiter 从队列移除且不泄漏槽位，后续后台正常获得；
- 重复释放不改变 `InFlight`。
