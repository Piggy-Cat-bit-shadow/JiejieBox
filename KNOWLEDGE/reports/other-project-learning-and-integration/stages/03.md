## 实际改动

### B01 XHTTP packet-up 预算（IMPLEMENTED_VERIFIED）

`transport/v2rayxhttp/conn.go` `packetUplink`：

- 修复“空队列接受整个超大 Write”的例外：一次 Write 按剩余预算分块追加，队列任何时刻
  `len(pending) <= maxPending`，调用仍返回完整 `n`（不改变调用方对短写的假设）。
- 新增内部账：`pending`（逻辑字节）、`inFlightBytes`（POST 持有、已出队但未释放）、
  `retainedCapacity`（数组 cap）、pending/in-flight 高水位、accepted/posted 累计；`stats()` 快照。
- 转移时序：write 接受 → flusher 取走并记 in-flight → POST 成功记 posted、in-flight 归零；
  失败字节不记 posted，随失败上报。
- 测试：`packetup_budget_test.go` 断言超大 Write 不越界、队列满时写阻塞、in-flight 单列、
  posted==accepted、高水位 <= 上限；原 `TestUplinkAmortizesSmallWrites` 与全套 xhttp 测试通过。

### B04 窗口返还审计（ALREADY_PRESENT_VERIFIED，XHTTP 路径）

`packetConn.Read` 直接读 response body，没有预取/提前返 window 的路径；H2/QUIC 库内缓存不可在本环境
证明，标 `NOT_VERIFIABLE_HERE`，不声称覆盖。

### B02 / B03 / B05 / B06 证据关闭

见 `explorations/data-plane-byte-budgets-2026-11-08.md`：TUN/UDP（子仓 pin）、relay 共享增长额度
（需要 04 反馈与真实长流基准）、reF1nd cached 首包移植（sing fork pin + 包装矩阵）、能力矩阵
（本轮未新增 wrapper，既有测试逐项列出）。均不是“以后再说”，报告给了重开条件。
