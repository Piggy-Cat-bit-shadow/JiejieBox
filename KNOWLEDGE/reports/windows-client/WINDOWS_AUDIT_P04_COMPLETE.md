## What this round cost, so it is not repeated

Five attempts went into this, and every one was a variant of the same mistake - **trusting a check
that does not model the real consumer**:

1. `git apply` accepted a patch whose hunk counts were wrong, because git is lenient.
2. A header recompute used a pattern that made the counts optional and wrote literal `0`s back.
3. A second recompute counted the artifact of splitting on `LF` as a context line.
4. The generator had a header pinned to a value copied from a log line, which silently re-broke
   the fix.
5. The splice added a trailing blank line the original does not have, which landed *inside* a hunk
   as an extra context line.

The durable fix is the one finally taken: generate the diff with the same algorithm the consumer
uses, and assert the two structural invariants that were being violated (no bare blank line before
a section header; the other sections byte-identical).
